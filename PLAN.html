Context 🔒 LOCKED

A web app for two retirement-age households (parents + in-laws) to do high-level budgeting and planning. The user is the developer + admin. Real users will probably log in once every 1–2 months to answer questions like “can we afford the Japan trip?” or “how are we doing this year?” Not a transaction tracker — a planning tool.

Design constraints:

  • Manual entry only, summary-level (monthly category totals; no per-line transactions).
  • Hosting must be free.
  • Privacy between households is non-negotiable.
  • Non-technical users on phone + laptop.
  • First-run experience must be guided and linear — users should not have to figure out what to do.
  • Scales to ~10 households without re-architecting.

v1 surfaces:

  1. Monthly + annual budget vs actual (categories like Groceries, Utilities).
  2. Big-ticket goals — named planned spends like “Japan trip $10k”, “New car $30k by 2027”. First-class object, not buried in a category.
  3. Cash flow / retirement runway — derived from monthly totals + net worth.
  4. Net worth snapshots — manual balance entry per account, monthly cadence.

Architecture 🔒 LOCKED

Invariants:

  • Every household-scoped table has a household_id column.
  • All reads/writes go through RLS using the user’s JWT.
  • The service-role key stays server-only, used only in admin dashboard server actions and the auth-webhook handler.

Stack 🔒 LOCKED

  • Next.js 16 (App Router) + TypeScript on Vercel Hobby. Personal use, not commercial.
  • Supabase free: Postgres + Auth (magic links) + RLS.
  • Tailwind + shadcn/ui — shadcn copies component source into the repo, so every default is overridable for older-user UX (font sizes, hit targets, contrast) without fighting a framework.
  • Brevo free SMTP (300/day, no sender-domain verification required).
  • Server Actions for all mutations; revalidatePath after writes.

Scaffolding produced Next.js 16, which has breaking changes from Next 15. Specifically: middleware.ts renamed to proxy.ts (export function proxy(...), Node runtime only); cookies() is fully async; Turbopack default. Auth + privacy — detailed 🔒 LOCKED

This is the security spine. Three concerns that get conflated but are separate:

  1. Authentication — proving who you are. Handled by Supabase Auth via magic link, delivered by Brevo SMTP.
  2. Authorization / privacy — controlling what you can see. Handled by Postgres RLS keyed on household membership (a many-to-many relation, not a single column on profiles).
  3. Accountability — knowing what was done by whom, and being able to cut off access. Handled by an audit_log table + admin dashboard + Supabase admin API.

Households are multi-user

Multiple email addresses can belong to one household. v1 roles:

  • owner — a family member of that household. Read/write on their own household. Can invite others to their household.
  • admin — the developer. Read/write on every household, plus access to /admin. Not a row in household_members; it’s a flag (profiles.is_admin).

Future roles (viewer, accountant, etc.) drop in by extending the role enum + RLS predicates; no schema rework required.

Invite flow

  1. Owner clicks “Invite” in Settings → enters invitee’s email (optional — the link works without it) and a role → server generates a 32-byte random token, stores hash in household_invites with expires_at (7 days), created_by, and the chosen role.
  2. App shows the link /join?token=… for the owner to share via whatever channel they want. If they entered an email, the link also goes via Brevo.
  3. Invitee opens link → if not signed in, magic-link login first → after auth, /join renders a confirmation form (not auto-redeem on GET, to prevent link-prefetcher abuse). On POST submit, the redeem_invite SQL function atomically claims the invite (race-free single-use), checks the email-binding when present, and inserts the membership row with the role from the invite.
  4. Tokens are single-use, expirable, and revocable from /admin.

Why Brevo (and what role it plays)

Supabase’s built-in SMTP is shared infrastructure capped at 2 emails/hour and is explicitly only for testing — they will throttle/block real apps. You have to point Supabase at some external SMTP. Options:

  • Brevo free — 300/day, no domain verification, ~5 minute setup. Wins on setup cost.
  • Resend free — 100/day but requires DNS-verified sender domain. More polished, more work.
  • AWS SES — cheapest at scale, slow to provision, sandbox mode by default.

Brevo is the right v1 pick. Supabase doesn’t talk to Brevo at runtime in any special way — it just uses Brevo’s SMTP creds. If we ever outgrow it, swap creds; no app code changes.

Session config (Supabase Auth dashboard)

  • JWT (access token) expiry: 3600s (default).
  • Refresh token rotation: ON.
  • Inactivity timeout: 90 days.
  • Absolute time-box: 365 days.

This is “stay logged in basically forever unless you don’t open it for 3 months.” Matches a 1-2x/month usage pattern — frequent re-auth would be a constant annoyance for older users.

Tradeoffs and what mitigates each:

  • Stolen device = stolen session for up to a year. User-facing mitigation: “Sign out everywhere” button calling supabase.auth.signOut({ scope: 'global' }). Admin-facing mitigation: revoke individual sessions from /admin/sessions.
  • Destructive ops. Delete-household, remove-member, etc. require a fresh re-auth challenge regardless of session age. 🟡 not implemented in Phase 1; deferred to UI work

Admin dashboard + revocation + audit trail

The admin needs to see who’s logging in, what they’re doing, and cut off access at will:

  • /admin route, gated on profiles.is_admin = true in the layout and at the top of each tab page (defense in depth).
  • Households tab — list each household, members, last sign-in, last activity. Per-member “Remove” button calls the atomic remove_member RPC (refuses if it would leave zero owners).
  • Sessions tab — list active sessions across all users (auth.admin.listUsers()). Per-user “Revoke sessions” button calls auth.admin.signOut(userId, "global").
  • Invites tab — list outstanding household_invites with revoke buttons.
  • Audit log tab — paginated viewer with the most recent 100 events. Filters by actor / action / household to land in Phase 2.

audit_log writes happen at three layers:

  1. Sign-in events — logged inline in /auth/callback right after exchangeCodeForSession succeeds. (Originally planned via Supabase Auth webhook, but the SDK doesn’t expose a clean “after sign-in” hook; inline is more reliable.)
  2. Sign-out + other lifecycle events — via the Supabase Auth webhook at /api/webhooks/supabase-auth. Verifies a shared SUPABASE_WEBHOOK_SECRET via constant-time compare; re-resolves the actor identity from auth.users (does not trust the payload).
  3. Sensitive mutations + admin actions — every server action that writes calls logAudit() before returning. Helper uses the service-role client so audit writes bypass RLS.
audit_log (
  id uuid pk,
  actor_profile_id uuid references profiles(id) on delete set null,
  actor_email text,           -- denormalized so the row stays readable after a user is deleted
  household_id uuid,          -- nullable for global/admin actions
  action_type text,           -- 'sign_in', 'sign_out', 'invite_created', 'member_removed',
                              -- 'account_created', 'snapshot_recorded', 'goal_updated',
                              -- 'session_revoked_by_admin', ...
  target_table text,          -- nullable
  target_id uuid,             -- nullable
  metadata jsonb,             -- shape varies by action_type; never PII beyond the email column
  ip_address inet,            -- x-vercel-forwarded-for preferred; raw XFF fallback for local dev
  user_agent text,
  created_at timestamptz default now()
)

RLS on audit_log: admin only. No regular user can read it (including their own rows) — keeps the dashboard honest and avoids leaking that another household exists.

Privacy tenants (RLS)

Three rules enforced by Postgres, not by app code:

  1. A user can only SELECT/INSERT/UPDATE/DELETE rows in households they’re a member of.
  2. Admin (the dev, via profiles.is_admin = true) bypasses #1.
  3. Anonymous (signed-out) sessions see nothing.

Policy template applied to every household-scoped table:

USING (
  is_member_of(household_id)
  OR is_admin()
)

is_member_of(), is_owner_of(), is_admin(), shares_household_with() are all SECURITY DEFINER functions with SET search_path = public. They avoid RLS recursion through the helper tables and are safe from search-path injection.

Gotchas baked into the migration:

  • Separate SELECT/UPDATE/DELETE policies (use USING) from INSERT policies (use WITH CHECK) — they aren’t interchangeable.
  • Wrap auth.uid() as (SELECT auth.uid()) — documented Supabase planner-caching tip.
  • Service-role key stays server-only. Used only by admin dashboard server actions, invite redemption, audit-log writes, and the auth webhook handler. Never imported by user-facing routes.
  • profiles has a column-level grant: REVOKE UPDATE … FROM authenticated; GRANT UPDATE(display_name) … TO authenticated. Belt + suspenders with the profiles_update_self policy so users can’t rewrite email to spoof identity in admin views. Consequence: admin profile UPDATEs must go through the service-role client.
  • One Playwright test in CI: signs in as user A, fetches every API route, asserts user B’s data does not appear. RLS leaks are silent — automate the check. 🟡 not yet written; waits for real Supabase project

Data model 🔒 LOCKED for identity/access/audit · 🟡 DRAFT for domain

All money stored as _cents integers (always positive; sign is conveyed by which table the row lives in, not by the value).

Identity & access 🔒 LOCKED

  • profiles — id (= auth.uid()), email (sourced from auth.users via trigger), display_name, is_admin boolean.
  • households — id, name, created_at, created_by (nullable; ON DELETE SET NULL).
  • household_members — household_id, profile_id, role enum (owner | viewer | accountant), joined_at. PK (household_id, profile_id). Default role is viewer for fail-safety.
  • household_invites — id, household_id, token_hash (SHA-256 of a CSPRNG token), email (nullable; enforced at redemption when set), role (enum, default viewer — the role the redeemer receives), created_by, created_at, expires_at, consumed_at, consumed_by.

Audit 🔒 LOCKED

  • audit_log — as sketched in the Auth section. RLS: admin-read-only. Writes always via service-role.

Domain — assets & liabilities 🟡 DRAFT

  • accounts — household_id, name, type (enum: checking / savings / investment / retirement / credit_card / mortgage / loan / other), is_liability boolean, current_balance_cents. For liabilities the balance is stored as a positive number; net worth math is SUM(assets) − SUM(liabilities). is_liability is the source of truth so the other type can be either.
  • account_snapshots — account_id, balance_cents, snapshot_date. Unique on (account_id, snapshot_date).

Domain — budgeting (expenses) 🟡 DRAFT

  • budget_categories — household_id, name, monthly_budget_cents (nullable), annual_budget_cents (nullable). Expense categories only. Seeded with ~10 defaults at household creation.
  • category_actuals — household_id, category_id, year, month (1–12), amount_cents. One row per category per month. Unique on (category_id, year, month).

Domain — budgeting (income) 🟡 DRAFT

  • income_streams — household_id, name (e.g. “Social Security”, “Pension”, “401k withdrawal”), expected_monthly_cents (nullable, used for projection). Stable list users edit only when their situation changes.
  • income_actuals — household_id, income_stream_id, year, month, amount_cents. Same shape as category_actuals so the monthly update wizard stays symmetric.

Domain — goals 🟡 DRAFT

  • goals — household_id, name (“Japan trip”), target_amount_cents, target_date (nullable), saved_cents (manual), status (planning/saving/booked/done/cancelled), notes.

Derived numbers

  • Net worth = SUM(accounts.current_balance_cents) WHERE is_liability=false − SUM(accounts.current_balance_cents) WHERE is_liability=true, taken from the latest snapshot per account.
  • Monthly cash flow = SUM(income_actuals) − SUM(category_actuals) for a given (year, month).
  • Annual cash flow = same, rolled up to year.
  • Budget vs actual = compare category_actuals to budget_categories.monthly_budget_cents / annual_budget_cents.

UI — older-user rules 🟡 DRAFT

  • Base font 18–20px. Buttons min 56px tall.
  • WCAG AAA contrast (7:1).
  • No hover-only affordances.
  • No hamburger menu. Flat bottom tab bar: Budget · Goals · Net Worth · Settings. (Cash-flow lives inside Budget as a summary card; standalone tab is overkill.)
  • Destructive actions confirm in a full modal, not a toast.
  • Money formatted $1,234 on dashboards; cents only on edit screens.
  • Icons always paired with text labels.
  • One primary (blue) action per screen.

First-run guided setup 🟡 DRAFT

Linear stepper, finishable in <5 minutes, can’t be skipped on first visit:

  1. Welcome — one paragraph in plain language.
  2. Name your household — text input.
  3. Add your accounts — repeat-add UI for accounts + current balance + asset/liability toggle. “Skip for now” allowed.
  4. Add your income streams — pension / SS / withdrawals / dividends. “Skip for now” allowed.
  5. Review default categories — show seeded list with current monthly-budget defaults, let them edit numbers or remove rows. “Looks good” continues.
  6. Add a goal (optional) — “Anything big coming up? Trip, car, repair?” Single-row form.
  7. Done — drops them on the Budget tab with a non-dismissable banner: “This month is empty. Add your first month’s totals when you’re ready.”

After first run, returning users always land on Budget. The wizard re-appears only if accounts is empty.

Monthly “Update” pattern 🟡 DRAFT

Two short wizards, surfaced as dashboard banners when overdue:

  • Update balances (net worth) — one screen per account: “Chase Checking: last $4,200 on Apr 15. Today?” Writes account_snapshots + updates accounts.current_balance_cents.
  • Update last month’s spending — one screen per category (and one per income stream): “Groceries — about how much in April?” Writes category_actuals / income_actuals.

Both are skippable per-step. Designed so a user who logs in after 2 months can catch up in 3 minutes.

No email reminders. They’ll come back when they need the app.

  1. Year+month integers vs. first-of-month date for category_actuals and income_actuals. Date is more flexible (date_trunc queries, range filters); integers match how non-technical users think. Recommendation: first-of-month period_start date with a CHECK that the day is 1. UI shows “April 2026”.
  2. Soft-delete on budget_categories and income_streams. Removing a category mid-year would orphan its actuals. Options:
    • (a) Hard delete with ON DELETE RESTRICT on actuals (forces user to delete actuals first — bad UX).
    • (b) Hard delete with ON DELETE CASCADE (loses historical data — bad).
    • (c) Soft delete via archived_at timestamptz. Actuals stay; UI filters archived from the create-new-actual picker. Recommendation: (c).
  3. Default seed categories. The plan says ~10: Groceries, Utilities, Housing, Transport, Healthcare, Insurance, Dining, Entertainment, Gifts, Misc. Confirm vs. let the user pick at onboarding. Recommendation: seed them, let onboarding edit/remove. Choosing from blank is paralysis.
  4. Goal “saved_cents” source. Manual entry as planned, OR derived from a designated savings account’s balance? Recommendation: manual for v1 (simpler, matches the rest of the manual-entry model). Reconsider in v2 if it’s annoying.
  5. Cash-flow card location. Plan says “cash-flow lives inside Budget as a summary card.” Confirm: top of the Budget tab, showing current month income vs expenses + 6-month runway projection?
  6. Net-worth chart granularity. Plot monthly snapshots? Per-account stacked, or aggregated? Default time range (12 months)?
  7. Onboarding skip-ability. The plan says “can’t be skipped on first visit.” Confirm we want a hard gate — users land on a blank Budget tab if they bail mid-onboarding and that’s confusing.
  8. Invite-creation UX. Owner’s view in Settings → “Invite” form should ask for: invitee email (optional), role (default viewer), expiry (default 7 days). Show the resulting /join?token=… link inline; the email send is opt-in. Confirm shape.

Key fixes that came out of the loop (all reflected in the data-model and auth sections above):

  • Atomic redeem_invite SQL function (race-free single-use, identity from auth.uid(), email binding, role from invite).
  • Atomic remove_member SQL function with CTE-based row locking (concurrent admins serialize on the same owner-row lock set).
  • safeNext allowlist (regex) replaces an earlier denylist approach.
  • Webhook canonical actor lookup with 404-vs-5xx distinction (404 = legitimate null actor; 5xx = retry).

  • Column-level grant on profiles restricting authenticated to UPDATE only on display_name.
